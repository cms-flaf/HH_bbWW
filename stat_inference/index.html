    Statistical inference¶

    The final step turns the merged histograms into datacards and runs limits with Combine, via the StatInference and inference submodules. See FLAF → walkthrough, stage 5 for where this sits in the pipeline.

    These commands run inside CMSSW/Combine, so prefix them with cmsEnv (or open one subshell):

    cmsEnv /bin/zsh        # a CMSSW+Combine subshell

    1. Make datacards and run limits¶

    One law chain takes the merged histograms all the way to the overlay limit plots. The datacard step itself consumes 1D shapes and does no rebinning of its own; the shapes this analysis feeds it are cut from the 2D DNN-vs-HME plane by a configurable preprocessing step the chain runs first — see Where the binning is decided:

    law run PlotResonantLimitsTask \
  --version dev \
  --hists-version VERSION_OF_THE_MERGED_HISTS \
  --era Run3_2022,Run3_2022EE,Run3_2023,Run3_2023BPix \
  --workflow local

    It runs, in order:

    Task Does
    PreprocessShapesTask runs the configuration's preprocess: step, if it declares one
    CreateDatacardsTask builds the datacards from the resulting shapes
    ResonantLimitsTask runs combine and combines the per-era cards per mass point
    PlotResonantLimitsTask draws the plots declared in the configuration's limit_plots

    Each limit_plots entry becomes one overlay of its datacard globs. An entry that also sets bands: true gets, in addition, the standard single-curve plot with the ±1σ/±2σ bands for each of its curves — the overlay draws expected lines only. Note the dhi task of almost the same name below (PlotResonantLimits, no Task): that is the one this task shells out to for the band plots.

    --version names what the chain writes; --hists-version names the Hists_merged tree it reads, so a re-binning or a re-fit does not require the input histograms to be reproduced under a new name.

    The datacard configuration is a set of cards, listed by name under StatInference.cards in config/global.yaml (StatInference.config instead names a single card file):

    StatInference:
  cards:
    DL_spin0: config/Datacards/DL/dl_spin0.yaml
    DL_spin2: config/Datacards/DL/dl_spin2.yaml

    Each card — DL_spin0 (DL/dl_spin0.yaml) and DL_spin2 (DL/dl_spin2.yaml) — declares the eras, channels, categories, mass points, processes and uncertainties; the chain reads them from there, not from global.yaml's own variable lists. Each card gets its own datacards, limits and plots, under Datacards/<card>/<era>/, ResonantLimitsTask/<card>/ and so on.

    The cards are built from shared files, each card listing the ones it uses under include::

    config/Datacards/
  systematics/              the uncertainties shared by DL, SL and the CI cards, one file per topic:
    luminosity.yaml           luminosity and pileup
    leptons.yaml              muon and electron ID, isolation and trigger; electron scale and resolution
    jets.yaml                 JES, JER, AK4 b-tagging, AK8 Hbb, Hcc, tau21
    parton_shower.yaml        ISR, FSR
  DL/systematics/           the DL-only uncertainties:
    theory.yaml               process theory (QCD scale, PDF+alpha_s, top mass)
    dy_reweighting.yaml       the DY reweighting's fit statistics and model variations
    dy_template.yaml          the DY templates and the low-mass DY estimate
    normalisations.yaml       TT/DY control-region normalisations, low-mass DY, Minor members
    cr_shapes.yaml            the control regions' DNN-shape nuisances
  DL/dl_common.yaml         the other settings the DL spin cards share, with the process model
                            of the preprocess step (members, drop, DY estimate settings)
  DL/binning_eqsig_DL_v2610.yaml  the DL binning only (see "Where the binning is decided")
  DL/dl_spin{0,2}.yaml      include every file above, then dl_common.yaml; add the signals,
                            their BR uncertainties and the limit plots
  SL/sl_common.yaml         the same for SL -- a skeleton for now, not in `cards:`
  SL/sl_spin{0,2}.yaml

    Includes do not nest, so each card lists every file it uses, explicitly (a card can point to another version of one of them). test/test_datacard_includes.py checks that the cards of one kind include the same topics, and every card every topic of systematics/, so a file forgotten in one card does not go unnoticed. The merge is strict: a top-level setting is made in one file only, and an entry of processes, uncertainties, limit_plots or impact_plots is defined once — anything set twice stops the chain with an error naming both files, never an override. A setting that differs between the spins therefore lives in each spin card, and one that differs between DL and SL in that channel's own files, not in systematics/. Include paths are relative to the including file. To see a card as the chain reads it:

    python3 StatInference/common/card_config.py config/Datacards/DL/dl_spin0.yaml

    prints each setting and entry with the file it comes from; every datacard and preprocess output also keeps the merged card it was built from, as card_config.yaml.

    ResonantLimitsTask, PlotResonantLimitsTask and PlotPullsAndImpactsTask run for every card, or with --card DL_spin0 for that card only: they then build, preprocess and fit just its datacards, so another card neither has to run nor can block it. Without --card, the plot tasks leave out (and name) a card that declares no plots. The StatInference block's param_values and hist_bins apply to every card; param_values builds each card for the requested masses it declares.

    Outputs from before the cards need a new --version

    Every output path now has a <card> level (Datacards/<card>/<era>/…, ResonantLimitsTask/<card>/…, LimitPlots/<card>, ImpactPlots/<card>). Run under a new --version: in one produced before, ResonantLimitsAndHistPlotTask's marker is already complete (it does not look at cards or eras), and old plot directories or HTCondor job files can be taken for the new ones.

    --era must hold every era behind the datacards

    Which eras get datacards and limits comes from the configuration's eras: and era_groups: blocks, not from --era. A real era listed inside an era_groups: entry is covered by that meta-era and is not built standalone, so with the Run 3 configuration the chain builds the Run3_22_23 combination of all four eras. --era must name every real era those cards read — here the four of Run3_22_23 — or the run stops with the cards need DL_spin0 Run3_22_23: …, which --era does not include. This holds with --card too: the datacard workflows' branch maps cover every card. Further eras are allowed and are not carded. CreateDatacardsTask and PreprocessShapesTask are one workflow each, with one branch per card and era (and mass), and their outputs (Datacards/<card>/<era>, Hists_preprocessed/<card>/<era>) do not depend on --era (FLAF → Eras).

    Where the shape uncertainties come from¶

    A type: shape entry in the configuration's uncertainties: list is only a declaration — it names a histogram the merger must already have written. What actually produces that histogram is the corresponding entry in config/Run3_<era>/weights.yaml, whose name: field is the datacard nuisance name plus a _{} placeholder for Up/Down. Adding a nuisance to the datacard configuration without adding it there fails with Cannot find histogram ...; adding it to weights.yaml without an expression: is worse, because the variation is then produced but is byte-identical to the nominal shape, giving a nuisance that constrains nothing and looks fine.

    A shape: entry costs more than a norm: one, and in a way that is easy to get wrong. A norm: entry is a weight expression evaluated on the central tree, so registering one and re-running the histTuple step is enough. A shape: entry names a shifted tree, and HistTupleProducer opens that tree in the anaTuple and in every AnalysisCache it reads (DNN, DeepHME). A source can therefore be present in the anaTuples and still fail, because the caches were produced before it was registered — the symptom is ERROR: tree Events__<source>__Up not found in file ... pointing at a luigi-tmp cache file, not at the anaTuple. Checking the anaTuple alone is not sufficient. Adding a new shape: source means regenerating the caches, so it belongs with an anaTuple production rather than a weights-only re-run.

    An event that only a shift moves into the selection (typically JES or JER) enters that shift's template with its real weight. The generator-level inputs of weight_base are listed in anaTuple_shift_invariant_columns (see Analysis), so the central tree carries them for that event too and the merge computes its weight_base. In anaTuples produced before that list existed such events had weight 0, so they were missing from the shifted templates.

    Correlating and decorrelating across eras¶

    There is no correlated: switch. Combine correlates two entries when they carry the same nuisance name and treats them as independent when the names differ, so the whole correlation model is expressed by naming — and, because the nuisance name is the histogram name, it is weights.yaml that decides it, not the datacard configuration.

    A source decorrelated per era carries the era in its producer name, so the four eras write four different histograms:

    # config/Run3_2022/weights.yaml          config/Run3_2023/weights.yaml
name: CMS_scale_j_2022_{}                name: CMS_scale_j_2023_{}

    and the datacard configuration then declares one entry per era, each scoped with eras::

    - name: CMS_scale_j_2022
  type: shape
  eras: [ Run3_2022 ]

    A correlated source keeps one name in every era's weights.yaml (CMS_btag_LF_{}) and one entry in the datacard configuration with no eras: field at all — an empty era list matches everything, which is what makes it apply to all four.

    Two consequences worth knowing:

    • Renaming a source to decorrelate it changes a histogram name, so it costs a HistMerger re-run. It does not need a new anaTuple production: the shifted trees are unchanged.
    • The two files must change together. Splitting weights.yaml without splitting the datacard configuration leaves the card asking for a histogram nobody writes any more (Cannot find histogram ... CMS_scale_j_Up), and it fails at datacard time rather than at merge time. Cross-check every card's type: shape entries against the producers of each era it declares before merging a correlation change.

    For a meta-era such as Run3_22_23, a nuisance scoped to one sub-era still applies: it varies that sub-era's contribution to the summed shape while the others contribute their nominal. The same holds for an lnN whose value differs per sub-era — lumi_1_13p6TeV is written into the card as a shape for exactly that reason, since one log-normal on the summed yield cannot express a factor that changes between eras. An lnN that does not depend on the era stays an lnN.

    b-tagging shape calibration¶

    The BTV shape calibration contributes eight nuisances — CMS_btag_LF, CMS_btag_HF, CMS_btag_{lf,hf}stats{1,2} and CMS_btag_cferr{1,2} — registered under norm: in each era's weights.yaml. Two things about them are deliberate:

    Boosted events are excluded at weight level. GetWeight in Analysis/hh_bbww.py folds weight_bTagShape_Central into the resolved branch only of its boosted ? ... : ... expression; boosted events carry weight_FatJetSF_Central instead. The variation expressions therefore read (boosted ? 1.0f : weight_bTagShape_<src>{scale}_rel) * final_weight, so a boosted event's varied weight equals its nominal weight and DatacardMaker's canIgnore threshold drops the nuisance from boosted categories on its own. Do not reach for unc_to_not_consider_boosted for this — that mechanism is commented out in FLAF/Analysis/HistMergerFromHists.py, so no code reads the key.

    The four *stats* sources are decorrelated per era, the other four are not. That follows the BTV prescription: LF, HF and the two cferr sources describe a common calibration and stay correlated; the {lf,hf}stats{1,2} sources are statistical and get one nuisance per era.

    How the split is expressed is worth understanding, because it is not a datacard-only change. The nuisance name is also the histogram name — DatacardMaker reads <process>_<name>_<Up|Down> — so an era-specific nuisance has to be named by the producer. Each era's weights.yaml writes name: CMS_btag_lfstats1_2022_{} and the datacard declares one entry per era scoped with eras:. A source that stays correlated keeps a single unsuffixed name in all four files. There is no separate "decorrelate" switch: whether a source is split is visible from what the merger writes.

    Two consequences to keep in mind. Renaming here is a merge-stage change only — HistTupleProducer keys off the weights.yaml keys (bTagShape_lfstats1, JER), and name: is read in exactly one place, FLAF/Analysis/HistMergerFromHists.py, so re-producing the histograms does not mean re-producing the shifted trees. And the two halves cannot drift silently: suffix the producer without the datacard, or the reverse, and the build stops with Cannot find histogram ....

    On the dc_make side this needs two things, both of which treat a real era as a one-element meta-era so configurations without era_groups: are untouched. DatacardMaker.uncAppliesTo registers the nuisance on the meta-era bin when any sub-era matches — Uncertainty.appliesTo compares against the meta-era name and would otherwise drop the entry silently, which is why the CMS_pileup_<era> block in the datacard configuration used to be commented out. getCombinedShape then varies only the matching sub-eras and takes the rest at nominal, which is what the lnN path has always done in _getSubEraLnNVariedShapes.

    lnN uncertainties needed neither change and can be split with no producer involvement at all: lumi_13p6TeV is two entries, eras: [Run3_2022, Run3_2022EE] and eras: [Run3_2023, Run3_2023BPix], because the luminosity calibration is a per-year measurement rather than a per-era one.

    Note also that config/Run3_2024/weights.yaml has no btag entries on purpose: config/Run3_2024/global.yaml overrides btag to HistTuple: none, so the weight_bTagShape_*_rel columns do not exist for that era.

    AK8 (fatbjet) calibration¶

    Corrections/fatjet.py supplies the mirror image for boosted events: three sources Hbb, Hcc and tau21 (FatJetCorrProducer.fatjet_Sources), registered as CMS_bbww_ak8_{Hbb,Hcc,tau21}. Because GetWeight puts weight_FatJetSF_Central in the boosted branch, the guard runs the other way — (boosted ? weight_FatJetSF_<src>{scale}_rel : 1.0f) * final_weight — so it is the resolved events that are neutralised, and canIgnore drops these nuisances from resolved categories.

    Two differences from the btag block are worth knowing when reading the resulting nuisances rather than fixing them:

    • There is no renormalisation step. btagShape has UpdateBtagWeight restoring the per-(channel, nJet) yield; the AK8 SFs have no equivalent and need none, so these nuisances legitimately carry a normalisation component.
    • Hbb applies only to hadronFlavour == 5 and Hcc only to == 4 (FatJetCorrProvider::sourceApplies, Corrections/fatjet.h). Hcc is therefore tiny for most processes and will fall under the canIgnore threshold in many categories.

    The calibration files are per-era and cover the four 2022/2023 eras only, so as with btag there is nothing to register for Run3_2024. They are decorrelated per era for the same reason the btag *stats* sources are: four separate files means four independent fits.

    Where the binning is decided¶

    By a preprocessing step the datacard configuration declares, not by anything in the chain's own logic. PreprocessShapesTask runs whatever preprocess: names, supplying --input, --output, --era and --config; it knows nothing about what the step does. A configuration with no preprocess: block skips the task entirely and the datacards are built from the merged histograms unchanged, so an analysis that needs no preprocessing is unaffected.

    The DL cards (DL/dl_spin0.yaml and DL/dl_spin2.yaml, through their shared DL/dl_common.yaml) plug in Analysis/EqualSignalBinning.py. For every mass, channel and category it:

    • reads the DNN score DNN_M<MX>_Signal in the category's frozen HME window: the sub-regions <region>_HMESub_m<MX> (Analysis/hist_booking.py) of the flavour Signal_Extraction_DL_window (config/sub_regions/hme_DL_v2610.yaml). The control regions use their jet category's window. The sub-region histograms are filled only with events inside the window, so there is nothing to cut here. With windows: in the binning configuration it instead cuts the windows out of the 2D DNN_m<MX>_vs_HME histograms;
    • carries the members of the QCD-scale and PDF uncertainties (members: in the cards) to the final bins; the datacard maker reduces them (7-point envelope, Hessian) on the summed eras;
    • merges the processes into the card's backgrounds (TT, DY, ST, Minor) and writes the members' theory and normalisation uncertainties, and the control regions' DNN tilts, as shapes;
    • replaces the sparse, partly negative-weight DY MC with a smooth fit template (Analysis/DYTemplate.py) in the same-flavour resolved SR and in SR boosted. Each template is compared with the raw MC it replaces, bin by bin (template_pulls in binning.json, with a warning beyond guard_sigma);
    • bins the DNN score from the top down: the SR into equal-signal bins, the control regions into control_region_bins (5) bins of equal background. A bin closes only once every background passes the statistics and positivity gates, for the nominal and every variation.
    preprocess:
  script: Analysis/EqualSignalBinning.py
  args:
    - --binning-config
    - config/Datacards/DL/binning_eqsig_DL_v2610.yaml
    - --jobs
    - 8

    --jobs bins that many masses in parallel, one process each. On HTCondor, give PreprocessShapesTask as many CPUs (--PreprocessShapesTask-n-cpus 8, or through LAW__). The task stages every mass's inputs (~50 GB for 25 masses), so a local run needs LAW_TARGET_TMP_DIR on a large disk rather than the shared /tmp.

    What is configured where¶

    Every run of the step rebuilds every shape and every uncertainty in the bins it applies, per era, from the merged histograms and the card. Its configuration is in three places, with no overlap (Analysis/preprocess_config.py reads and checks them, and raises on an unknown key):

    what where
    the binning: bin targets n_bins, gates, control_region_bins (and windows for 2D inputs) the binning file, DL/binning_eqsig_DL_v2610.yaml (--binning-config), or saved edges (--edges)
    the process model: which merged-histogram processes make each background (members), where a member is left out (drop, card categories), the DY template and low-mass DY settings preprocess: of the background processes in DL/dl_common.yaml
    every uncertainty the step builds: its name, scope (processes, channels, categories) and value preprocess: of the type: shape uncertainties in DL/systematics/

    An uncertainty's preprocess: holds exactly one of:

    preprocess: { member_values: { TT: 0.025, ttV: [ -0.03, 0.03 ] } }  # nominal + value x member nominal
preprocess: { cr_tilt: 0.04 }                  # DNN tilt of its one process in its categories
preprocess: { dy_template: tail }              # (or fit_only) the DY template in its channels and
                                               # categories; the nuisance is the template's band
preprocess: { lowmass_dy: [ 0.0, 2.0 ] }       # the low-mass DY estimate in its categories, scaled
                                               # by these factors for Down / Up

    The name of the entry is the nuisance written. For cr_tilt, dy_template and lowmass_dy its scope is where it is built: a DY template or the low-mass estimate is applied exactly where its nuisance is declared. A member_values variation is built in every category of the backgrounds holding its members (and is checked by the binning gates there); its categories: and channels: only decide where the datacard maker applies it. The datacard maker reads entries with .get() and ignores preprocess:. A mistyped preprocess key on an uncertainty is not silent either: the step then writes no histograms for it, and the datacard maker stops on the missing shape.

    • To change an uncertainty, change its entry in the systematics file; the next preprocess run rebuilds it. Changing a value can move the bin edges through the gates (which hold for every variation); to keep the edges, reuse them with --edges.
    • To rebin, change the binning file only (other n_bins targets or gates).
    • To reuse a binning, give the step a binning.json it wrote, --edges <file> (relative paths starting with config/ are resolved in the analysis area, so commit it under config/Datacards/DL/), in place of or next to --binning-config. The edges of the card's era are applied as they are; with a binning configuration too, a bin that fails its gates is only a warning. Recomputing the edges stays the default.

    The derived binning.json (edges, yields and template pulls per window) is a product, not configuration, and is written into the task's output beside the shapes it produced.

    A group era from era_groups: is binned on its members' summed statistics. Its output keeps the sub-eras separate (Run3_22_23/{Run3_2022,Run3_2022EE,…}) so the per-era uncertainties survive to be combined in the datacard maker.

    EqualSignalBinning.py is a plain executable (run it in the CMSSW environment, which has iminuit), so a binning can be inspected without going through the chain:

    cmsEnv python3 Analysis/EqualSignalBinning.py \
  --input  "$ANALYSIS_BIG_DATA_PATH/VERSION_OF_THE_MERGED_HISTS/Hists_merged" \
  --output /tmp/$USER/eqsig_Run3_22_23 \
  --era    Run3_22_23 \
  --config config/Datacards/DL/dl_spin0.yaml \
  --binning-config config/Datacards/DL/binning_eqsig_DL_v2610.yaml \
  --masses 300,800 --jobs 2

    The datacard bins are named without a / (SR_res2b, TT_res2b, DY_res2b, …), because dhi's impact merging cannot handle one. input_categories maps each name to its directory in the histogram files, the sub-region of the mass being built (SR_res2b: SR_HMESub_m${MX}/res2b, TT_res2b: TT_CR_HMESub_m${MX}/res2b, …); StatInference substitutes ${MX}.

    The generic StatInference/bin_opt_2d/rebin_2d.py (with config/Datacards/DL/binning_hmebox.yaml or DL/binning_2d.yaml) was the DL card's earlier preprocessing step. It is still available to a card that wants an HME window or DNN slices without the control regions and DY templates.

    There is also StatInference/bin_opt/, an offline combine-driven search over candidate binnings feeding the hist_bins option. This analysis does not use it, and leaves hist_bins unset.

    Datacards on their own¶

    To build cards outside the chain — a quick check on shapes that are already rebinned:

    cmsEnv python3 StatInference/dc_make/create_datacards.py \
  --input  PATH_TO_REBINNED_SHAPES \
  --output PATH_TO_CARDS \
  --config config/Datacards/DL/dl_spin0.yaml

    2. Run limits on existing datacards¶

    For cards you already have on disk, the dhi task can be called directly:

    law run PlotResonantLimits --version dev --datacards 'PATH_TO_CARDS/*.txt' --xsec fb --y-log

    Hints:

    • add --workflow htcondor to submit to the batch system (local by default);
    • add --remove-output 4,a,y to clear previous outputs;
    • add --print-status 0 to get the workflow status and the output file name;
    • options and background: the cms-hh inference documentation.

    3. Pulls & impacts¶

    Declared in the datacard configuration's impact_plots block and drawn by PlotPullsAndImpactsTask, which writes to <version>/ImpactPlots/<card>/<name>/<era>/<mass>/ on fs_default beside the limit plots:

    law run PlotPullsAndImpactsTask \
  --version dev \
  --hists-version VERSION_OF_THE_MERGED_HISTS \
  --era Run3_2022,Run3_2022EE,Run3_2023,Run3_2023BPix

    impact_plots:
  - name: combined
    masses: [ 300, 600, 800 ]
    poi_value: limit
    plot_params:
      method: default
      order_by_impact: true
      mc_stats: false

    poi_value is the signal strength the Asimov dataset is built at, and it has to be near the limit to mean anything. dhi's default is r=1, which on this scan is an almost invisible signal at 300 (limit ~6.8) and ten times more than can be excluded at 800 (limit ~0.065) — the first gives a background-only ranking, the second pins r and collapses every impact to ~0. limit reads the expected limit for each mass from the limits already merged for those cards; a number sets it directly.

    Changing poi_value does not move the outputs

    It reaches combine as --expectSignal through PullsAndImpacts' custom_args, which is significant for task identity but not part of the store path — every value writes to the same file. Clear PullsAndImpacts, MergePullsAndImpacts and PlotPullsAndImpacts for that version under inference/data/store before re-running with a different one, or law reports the old fit as complete and you get the previous ranking. It cannot go through dhi's parameter_values either: with hh_model=NO_STR, POITask hard-codes both the joined values and the postfix, dropping it silently.

    Each entry becomes one dhi PlotPullsAndImpacts per era and mass, and the plots land in <version>/ImpactPlots/<card>/<name>/<era>/<mass>/, with the card in the file name too (the default plot_postfix).

    With no glob:, an entry uses the combined card ResonantLimitsTask writes at data/<version>/Datacards/<card>/combined/combined_<mass>.txt — every era and category in one fit, which is the ranking that describes the result. It is drawn once and labelled combined.

    To rank a single category instead, give the entry a glob:, resolved against that era's datacard directory with ${ERA} substituted, the same idiom limit_plots uses:

      - name: res2b
    glob: "${ERA}/categories/SR_res2b/*.txt"
    masses: [ 300, 600 ]

    The glob and the mass must select exactly one card: PullsAndImpacts fits a single workspace, one combine job per parameter, so it cannot be handed a set. If it matches none or several, the error names the directory and lists what is in it. Note dhi draws one plot per card — it cannot split a card into per-category panels — so per-category rankings come from pointing at the per-category cards, which the chain already writes.

    plot_params accepts any PlotPullsAndImpacts parameter and is checked against them, so a typo is refused rather than ignored. hh_model is pinned to NO_STR: this is a resonant search, and the dhi default would otherwise fit r alongside kl, kt, CV and C2V, against a workspace other than the one the chain built.

    What a mass costs depends on method

    With method: default — what this analysis uses — dhi fits each nuisance separately, roughly two combine jobs per nuisance per mass (~160 here), so it is worth sending to a batch system. method: robust instead runs one fit per mass and reads every impact off the inverted Hessian (minutes for all three masses), but can drop parameters (below). create_branch_map in dhi/tasks/pulls_impacts.py is where the difference lives. To redraw without refitting, pass --redraw together with --remove-output 0,a,y (and --card): once a card's plots exist the task is complete, and --redraw alone does nothing.

    method: robust can silently drop a nuisance

    robustHesse removes parameters it cannot invert, logging Dropping <name> from the hessian and then exiting successfully. The dropped nuisance is simply absent from the plot and the merged JSON, with nothing marking its absence — on the earlier Run3_Early cards this happened to CMS_res_j. The task diffs the fitted parameters against the card's own nuisance lines afterwards and warns, naming what went missing; take that warning seriously before reading a ranking as complete.

    mc_stats needs parameters_per_page

    The combined cards carry a few hundred autoMCStats bins, so mc_stats: true puts ~460 parameters on the plot. parameters_per_page defaults to -1, meaning a single page, and the result is an unreadable hairline strip rather than an error — so the task refuses the combination. Set parameters_per_page: 25 alongside it.
